# CodePilot Edu 项目计划书（指导教师审阅稿）

项目名称：CodePilot Edu——面向工科程序设计课堂的 AI 分层纠错与教学辅助系统

编制日期：2026年10月23日　审阅提交目标：2026年10月25日前

## 一、项目摘要

CodePilot Edu 面向软件工程、物联网工程等工科专业学生及程序设计课程教师，聚焦课堂练习中学生遇到错误后难以及时获得指导、教师难以同时掌握个体困难的问题。系统设计包括代码评测、失败依据展示、递进纠错提示、学习过程记录和教师查看功能，将学生自主修改与教师针对性辅导衔接起来。

首期围绕 C 语言基础练习，打通“提交—评测—提示—修改—再次提交—教师查看”流程，形成可演示原型及小范围验证材料。项目以课堂辅助为定位，支持学生在理解问题的基础上继续练习，并为教师安排辅导提供可追溯依据。

## 二、需求与应用场景

需求依据来自团队课堂观察：现有教学主要采用教师讲授、学生使用 IDE 练习的方式。IDE 能提供编写、编译和调试支持，困难集中在报错信息向学习指导的转化，以及多人练习时辅导资源的分配。

学生遇到编译报错、输出不符或程序无法结束时，需要判断先检查什么、如何验证修改。仅看到报错或最终答案，未必能够理解原因。教师巡视答疑时，需要了解学生已经尝试过哪些修改；只看当前代码和最终成绩，难以还原其卡点，也不易区分偶发失误与持续困难。

首轮验证计划访谈1名任课教师、5名学生，并结合受控操作观察。访谈围绕最近一次代码错误及求助方式，操作观察检查提示能否被理解、学生能否据此继续修改、教师能否根据记录确定辅导对象，以及新增提交步骤是否打断原有练习。记录任务、耗时、提示理解偏差和操作障碍，保留匿名原始记录；该样本用于发现问题，不用于推断普遍需求比例或教学成效。

## 三、产品与功能设计

学生继续使用熟悉的 IDE 编写程序，进入系统选择练习并提交源代码。系统分配提交编号，完成受限编译和测试，分别展示编译诊断、运行状态及可公开测试样例中的预期与实际输出。错误反馈以本次执行记录为依据，避免只给出“答案错误”的结论。

提示按三个层次递进：第一层指出应检查的现象或位置；第二层解释相关知识点并提出检查问题；第三层给出局部修改方向与验证方法。学生按需请求下一层提示，再修改并提交；默认不直接给出整题替代答案。以循环边界问题为例，提示先引导检查执行次数，再讨论边界条件，最后指导使用小输入验证。

系统按提交保存代码快照、评测结果、提示层级及时间，将前后版本关联。教师查看持续失败的练习、提示使用情况和修改轨迹，据此决定个别辅导或集中讲解；系统提供线索，教师作出教学判断。

| 功能范围 | 首期交付边界 | 后续扩展 |
|---|---|---|
| 练习与评测 | C 语言基础题、代码提交、受限编译与测试 | Java、Python 评测适配 |
| 纠错提示 | 结合失败依据的三级提示与重新提交 | 扩充课程典型错误及提示模板 |
| 过程与教师查看 | 提交快照、提示记录、连续失败筛选和单人轨迹 | 更丰富的班级分析与教学平台对接 |

首期题目覆盖输入输出、分支、循环、数组和函数等基础内容，优先选取可明确复现失败原因的练习，不扩展为综合课程管理平台。

## 四、技术方案与实施条件

系统架构采用 Vue 3、Python + FastAPI、SQLAlchemy 和 MySQL。Vue 3 承载学生提交、反馈展示与教师查看页面；FastAPI 处理权限、提交和记录查询；数据通过 SQLAlchemy 访问 MySQL，关联课程、题目、提交、评测与提示记录，便于查询、备份及版本调整。

C 语言评测采用 GCC 和受限 Docker 环境。评测任务与业务服务分离，限制运行时长、内存、进程数及输出量，禁用评测容器外网访问，采用非特权运行和独立临时目录，任务结束后清理资源。原型阶段采用低并发队列，先验证结果可复现与异常可恢复。

AI 能力通过模型 API 接入，将题目要求、必要代码和编译测试证据组织为提示上下文。评测结果与模型解释分别保存，模型解释不能覆盖执行事实。接口设置超时、调用额度与失败处理；模型不可用时保留评测反馈和规则提示，资源或接口故障不计作学生代码错误。开发复用现有电脑，形成环境配置、接口说明、数据库结构和部署步骤，减少交接与维护负担。

## 六、推广与服务模式

项目从一门课程、小范围受控试用开始。任课教师或课程负责人选择练习、检查测试依据并决定使用环节；学生完成练习并反馈操作体验；学校或院系负责教学使用条件、数据管理和资源安排。首轮参与人数属于验证安排，不作为已有用户规模。

推广依据是完整演示、可复核记录和问题修复结果。先验证课堂流程能否顺畅衔接，再讨论扩大试用。服务内容围绕题目与测试适配、环境配置、使用说明和维护支持展开。付费主体按“院系或课程经费”作为假设，是否采购由实际预算与需求决定。后续收费与续期依据课程范围、部署维护量及服务记录协商；本期不设置收入和增长预测。

## 九、风险与应对措施

诊断可靠性方面，编译信息可能存在连带报错，测试也不能覆盖全部逻辑错误。系统展示证据来源，区分确定的运行现象与模型给出的原因解释；教师复核典型样本，发现误导提示后修订模板并复测。

运行安全方面，死循环、资源滥用和恶意代码会影响评测环境。通过限时限额、隔离执行、任务清理与异常日志控制风险，先验证隔离措施，再开放受控提交。

课堂使用方面，额外操作和过度依赖提示会削弱练习价值。保留原有 IDE 流程、减少提交步骤，由教师确定提示深度和使用时机。学习记录按角色授权访问，访谈使用匿名编号，发送模型 API 的内容限于必要代码与证据，避免附带姓名、学号等身份信息。
